# 内网模型语义抽取试验

试验日期：2026-09-23。使用用户提供的内网 OpenAI 兼容接口，模型 ID 为 `deepseek-v4-flash-0731`。API 密钥只在运行时经终端隐藏输入传递，未写入代码、配置、提示词或结果文件。输入仅为本目录的公开报告节选，未发送澄岳项目资料。

## 任务和评分口径

这是**给定字段名称的受限抽取**：模型收到指定 PDF 页的带 ID 文字块或表格行，以及待填写字段清单，须返回 `status / value / unit / source_ref`。四种状态是 `found`、`missing`、`not_applicable`、`unknown`。评分要求状态、值、单位以及来源定位同时正确；对于数值，引用的原文块必须直接包含该数值。模型输出仅是待审候选，脚本没有写入项目事实库。

| 样本与轮次 | 输入范围 | 人工标注字段 | 严格通过 | 状态正确 | 来源定位正确 |
| --- | --- | ---: | ---: | ---: | ---: |
| 北京可研，初始提示 | PDF 第 6、7、8、177 页；118 个原文 ref | 25 | 20/25 | 25/25 | 22/25 |
| 北京可研，收紧来源与空值要求 | 同上 | 25 | 24/25 | 25/25 | 24/25 |
| 江门环评，跨类型测试 | PDF 第 5 页基本情况表；14 个原文 ref | 14 | 13/14 | 14/14 | 14/14 |

北京第二轮的剩余错误是“计划完工月份”：值 `2026-11` 正确，但引用的是只含“月底完工”的相邻文字块，未包含年份和月份。第一轮另有两个数值引用到相邻错误块，说明**答对值并不等于来源可追溯**。第二轮提示是在看到第一轮错误后收紧的，24/25 不能当作独立泛化指标。

江门环评中，模型正确区分了复选框的勾选项、投资、比例、用地面积和未知字段。唯一未严格通过的施工工期把 `value` 输出成“6 个月”、`unit` 输出成“月”；含义正确，但未遵守数值与单位分栏。现有确定性表头规则在这份环评表中形成 **0 条**数值候选，而模型从该复杂键值表中提取了 13 个严格正确字段。这表明模型对不同表格结构有帮助，也说明输出仍需模式校验。

## 开放式发现与关系抽取

为了检验“不预先给字段名”是否可用，另取晋江高坠事故调查报告 PDF 物理第 3、8、9、10 页。模型调用前先建立 17 项事实与 8 项关系的人工核对点（`llm-accident-gold.json`）。测试输入仅含 11 段相邻原文行拼成的连贯片段，每段保留 PDF 页码和原始文字块 ID；没有向模型提供核对点。

| 任务 | 模型输出 | 人工逐项核对 | 结论 |
| --- | ---: | ---: | --- |
| 开放式事实 | 18 项 | 15 项可作为待审候选；3 项需修正 | 时间、人数、损失及若干原因摘要可定位，但“地点”混入项目描述，“籍贯”标签超出原文明确含义，“发包”被改写成“转包”。 |
| 第一轮关系 | 13 条 | 4 条有明确方向性原文支持；9 条不成立 | 把同一段并列的间接原因擅自连成“导致”；还写出原文不存在的“事故隐患未被及时发现和消除”。 |
| 收紧因果连接词与引文后 | 3 条 | 3 条均有直接引文，且引文能在来源片段中定位 | 错造关系减少，但两条的目标仍把多个事件合在一个节点里，无法直接入图。此轮是在看到首轮错误后调整提示，不能视为独立泛化成绩。 |

开放式事实输出虽覆盖了不少核对点，却没有形成足够细的结构：`900KW` 被埋在“事故地点”值里，防护用品、警示标志、踩踏、断裂、坠落被合并成一段“直接原因”。它适合给审核员看摘要，**不足以直接建立事实台账和可计算的因果图**。关系任务尤其说明：真实 `source_ref` 只证明模型指向了存在的段落，不能证明该段落支持所写的**关系方向**。

原始输出保存在 `llm-eval/accident_facts_response.txt`、`accident_relations_response.txt`、`accident_relations_v2_response.txt`。人工逐项判定及理由在 `llm-eval/accident_open_review.json`，运行元数据在 `llm-eval/accident_open_metadata.json`。评分是针对这四页、这一模型和这些提示的人工审查结果，不代表全篇、其他报告或多次运行的准确率。

## 产物与复跑

- 人工答案：`llm-beijing-gold.json`（25 字段）、`llm-eia-gold.json`（14 字段）。
- 代码：`backend/scripts/evaluate_llm_extraction.py`、`backend/scripts/evaluate_llm_eia.py`；两者均从终端隐藏读取密钥。
- 开放式试验：`backend/scripts/evaluate_llm_open.py`，同样隐藏读取密钥；默认运行事实与首轮关系，`--task relations_v2` 仅运行收紧后的关系提示。
- 本目录 `llm-eval/` 保存各轮模型原始 JSON 和逐字段评分 JSON；这些文件不含 API 密钥。北京的 `run1`、`run2` 分别保留，避免用后一次覆盖前一次。

在 `report-platform/backend` 目录执行，`<内网接口>` 由操作者填写，命令运行后再在隐藏提示处输入密钥：

```bash
../.venv/bin/python scripts/evaluate_llm_extraction.py --base-url '<内网接口>' --model deepseek-v4-flash-0731 --prompt-version 2
../.venv/bin/python scripts/evaluate_llm_eia.py --base-url '<内网接口>' --model deepseek-v4-flash-0731
../.venv/bin/python scripts/evaluate_llm_open.py --base-url '<内网接口>' --model deepseek-v4-flash-0731
../.venv/bin/python scripts/evaluate_llm_open.py --base-url '<内网接口>' --model deepseek-v4-flash-0731 --task relations_v2
```

## 开发判断

可以把模型加入**候选语义抽取**，尤其用于跨版式字段、复选框和文字判断。但现阶段只能作为人工审核前的一层：服务端必须校验字段模式、原文 ref、数值/单位、缺值状态和计算关系；错引、无源或冲突项要进入待审队列。关系还需要单独验证触发原文、方向和节点粒度；不能仅凭引用存在就接纳。模型不能直接写入项目事实、替代确定性计算或宣布报告可发布。

本次测试覆盖三份公开报告的少量指定页；开放式发现与事故过程关系只测了单一事故报告，且细粒度不足。没有测全篇 205 页、跨页证据链、其他类型报告的论断与证据关系、扫描件 OCR 后抽取、长文写作或稳定性重复运行。下一步适合先实现**原文定位 → 原子候选 → 人工确认**的审核链路，并以新的报告页做盲测；关系候选只允许带可核对触发引文的明确原文边，分类关系另行处理。
