# 语构 · 通用专业报告平台产品需求文档

版本：2.2

基线日期：2026-09-26

定位：面向私有化部署的专业报告写作与核对平台

当前阶段：本机运行、单人操作的可验证原型

## 1. 文档目的与阅读方式

本文同时记录产品目标、当前可操作范围和后续需求。**“已实现”只表示表中限定的行为已经实现，并有相应测试或操作记录；不表示整个通用平台已经完成。**

后续开发按[开发清单](开发清单.md)推进；数据、接口和实现约束见[详细设计文档](详细设计文档.md)。每次交付必须同步更新需求状态、清单和验证证据。早期方案中的领域包、权限、双向语义 Diff 等内容保留为目标，不能据此对外宣称已经实现。

| 状态 | 含义 |
|---|---|
| 已实现 | 本文明确范围内存在可操作入口、后端行为与验证证据 |
| 部分实现 | 已有可用子流程，但未覆盖目标需求的全部范围 |
| 待开发 | 当前没有完整用户操作路径 |
| 待验证 | 实现或设计存在，但缺少足以支持产品结论的测试 |

历史测试结果以发生时的记录为准。本轮后端全量运行 81 项为 80 通过、1 个 CAT-13 夹具预期失败；修正预期后相关测试文件复跑 11/11 通过，尚未宣称修正后的全量回归 81/81。前端全量浏览器 11/11 通过，构建通过。独立测试库的90次移除、5个固定输入案例与 S4/S7.1 真实模型验收见[30类资料配置与推演验收](30类资料配置与推演验收.md)；旧 55/9 基线见[UI 优化与验收](UI体验优化与验收_2026-09-24.md)。

## 2. 产品目标与当前结论

### 2.1 用户要完成的工作

用户提供本项目材料，建立有来源的事实台账，选择适用的历史写作结构或直接起草，在编辑器中形成报告，再核对数值、来源与保留事项，导出可追溯的文档。

平台应减少四类错误：历史数值误用、计算与正文不一致、无证据的确定性结论，以及修改事实后遗漏关联段落。优先建设对这条流程有实际作用的功能。

### 2.2 当前已经能做什么

- 新建空白项目，上传 PDF/DOCX，查看原文和位置；配置模型后逐页抽取待审事实，人工修改、拒绝或确认入台账。
- 手工建立事实及来源，运行受限 Decimal 规则，预览变更与下游影响，确认后保存修订。
- 浏览已入库的澄岳精密 30 类历史资料、117 个原始资产及只读局部图谱。
- 在新项目明确选择历史语料版本，按章节查看 30 类作用、配置使用方式并小批模拟移除影响；映射本项目事实、审核写作包，预览候选后确认加入 Plate。
- S4/S7.1 模型起草可先查看受审输入快照，再核对候选实际引用；目前仍是两章限定能力。
- 在 Plate 编辑标题、正文、引用块、列表、表格、链接和事实引用，保存、刷新、比较版本，核对后导出 DOCX、PDF 和审计记录。
- 在证据不足或存在关键冲突时生成有明确状态的预审稿，阻断正式导出。

### 2.3 “30 类资料用于写作”的准确口径

**30 类已经全部入库并可查看，但没有证据证明 30 类都直接用于成稿，也不要求每个新项目固定生成 30 类。** 当前上传文件的抽取功能主要形成可定位原文、待审事实、调用记录与已确认事实，尚不能自动生产澄岳样本那样完整的 30 类语料。

在澄岳三个章节的 guided 写作实验中：

| 范围 | 实测结果 |
|---|---|
| 8 类留下段落来源回链 | 04 章节、09 切块、10 骨架、13 规则、15 论断、18 证据目录、23 冲突、27 模板；各自贡献不同，来源回链不等于独立类别必需 |
| 4 类仅在包内或核对中出现 | 12 节点、19 摘录、24 缺口、26 文风；其中摘录入口实际用于来源核对，未写入候选段落回链 |
| 18 类未观察到记录级写作消费 | 仍可用于浏览、来源定位或审计；当前实验不足以证明它们无用 |
| 引导成稿覆盖 | S4 首年需求与销售、S7.1 设备报价身份、S5.2 配电冲突预审披露 |
| 其他章节 | 其余 46 个章节可浏览写作包与来源，尚无已验证的引导成稿规则 |
| 模型路径 | S4/S7.1 的受审最小包经真实模型各两次请求：首次取消、再次确认；确认后有2个待人工核对的工作稿事件与模型审计。DOCX/PDF/审计预审导出核对通过，正式交付仍受缺证阻断 |

逐类结论见[30 类资料写作应用清单](30类资料写作应用清单.md)与[写作支撑验证报告](写作支撑验证报告.md)。产品判断必须来自实际用户动作、段落来源与受控实验，不能来自“文件存在”“页面能打开”或“某段代码依赖它”。

## 3. 用户、场景和部署边界

### 3.1 用户角色

| 角色 | 需要完成的任务 | 当前实现 |
|---|---|---|
| 撰写人 | 录入事实、选参考、起草、编辑与处理问题 | 已有操作入口 |
| 核对人 | 查看原件、核对事实修订、检查报告并确认 | 同一本机操作者执行；没有独立账号或审批权限 |
| 资料维护人 | 核对语料身份、文件、来源、用途和版本 | 内置语料只读浏览；通用发布工作台待开发 |
| 部署维护人 | 安装、配置模型、备份与恢复 | 开发运行说明和模型配置已提供；生产运维体系待开发 |

角色是业务分工，当前不是权限系统。现版本没有登录、账号、组织、角色授权和多人协同；项目 ID 隔离不能代替身份鉴权。

### 3.2 首要场景

1. 从本项目文件抽取或手工录入少量关键事实，核对来源后形成报告。
2. 复用历史章节的结构、槽位、论断边界和规则模式，替换为本项目事实。
3. 事实变化时查看计算结果与报告引用影响，再更新正文并重新核对。
4. 证据不足时输出明确标为预审的报告，给出下一步待补内容。

### 3.3 不纳入当前交付承诺的能力

- 任意行业、任意类型报告的自动全篇成稿与自动专业审签。
- 对任意文件自动完整抽出 30 类且无需人审。
- Plate 演示站全部插件、任意 Word 版式无损往返、复杂图文排版。
- 完整的双向语义 Diff、自动改写所有受影响论断、版本一键回滚。
- 团队权限、实时协同、生产级多租户、公网部署。
- 已生成的语义向量或基于向量的语料检索；现有向量文件为零行。

首期采用 React、TypeScript、Python、PostgreSQL 和 Plate。当前不依赖 Semantica、向量库或独立图数据库；后续是否引入，以可验证的用户收益决定。

## 4. 信息与状态模型

### 4.1 核心对象

| 对象 | 用户视角的含义 | 归属与边界 |
|---|---|---|
| 项目 | 一次独立写作任务的材料、事实、规则和报告 | 稳定 `project_id`；新项目事实为空 |
| 项目文件 | 本项目上传的 PDF/DOCX 原件及可定位片段 | 项目独立；原件保留摘要与来源位置 |
| 抽取候选 | 模型或表格解析提出的待审信息 | 不等于正式事实；确认前不参与权威计算 |
| 项目事实 | 本项目已录入或确认的值、单位、口径和时点 | 有稳定 key、状态与修订；不是历史语料节点 |
| 项目规则 | 对本项目事实进行确定性计算的表达式 | 输入依赖、目标事实与规则身份可追溯 |
| 历史语料 | 原文、结构、骨架、图谱、证据与质量记录的只读版本 | `corpus_id` 与版本固定；历史值不自动继承 |
| 章节写作包 | 当前章节可用或拒用的历史条目、本项目映射与问题 | 每项有类别、资产、记录身份和使用边界 |
| 章节资料配置 | 本项目本章节的 30 类使用方式 | `auto/review/exclude` 持久化，保存后写作包重载，旧候选失效 |
| 移除模拟 | 用当前或示例事实比较类别变化 | 只读、纯内存；仅已适配章节可判断当前实现的变化 |
| 候选正文 | guided 或模型产生、尚未确认的章节文字 | 取消不写报告；模型候选必须人工审阅 |
| 报告版本 | 已保存的 Plate 正文及当时引用的事实修订 | 后续编辑产生新版本，旧版本保留 |
| 导出包 | 某一报告版本的 DOCX、PDF 和审计 JSON | 必须区分预审与经过当前平台闸门的正式导出 |

### 4.2 必须区分的状态

| 对象 | 状态规则 |
|---|---|
| 事实 | `DEFINED` 可包含有效值 0；`UNDEFINED` 表示未提供；`UNEVALUABLE` 表示计算依赖不足，不得写成 0 |
| 抽取结果 | 待审、确认、拒绝；确认保留来源和抽取运行记录，失败不得伪装为成功 |
| 事实来源 | 未核对、当前修订的原文位置已核对、由已核对输入计算；只证明软件记录的核对动作，不证明外部真实性 |
| 语料条目 | 可复用、待本项目核对、拒用；拒用原因须可查看 |
| 报告 | 候选 → 工作稿 → 已人工核对；能否正式导出由当前闸门共同决定，不是仅看按钮是否点击 |
| 过时引用 | 事实或规则输入变化后旧正文仍保留，但标为待更新；更新文字不能绕过修订与证据核对 |

“可交付”是业务目标，当前软件只能给出平台闸门结果。证据真实性、行业规范与专业判断仍由实际业务审核承担。

## 5. 用户主流程

### 5.1 新项目写作

1. **新建项目**：填写项目名，进入空白事实台账。
2. **准备材料**：上传 PDF/DOCX；按页或段查看原文。扫描页先识别，结果仍待核对。
3. **建立事实**：逐条审查抽取候选或手工录入；确认字段、值、单位、口径和来源位置。
4. **计算**：创建目标事实与受限规则；输入事实改动先看预览，确认后计算结果与修订一并保存。
5. **创建报告**：选择仅基于本项目事实起草，或明确选定只读历史语料版本及适用报告类型。
6. **选章节与来源**：按需查看 30 类在本章的作用、配置使用方式或进行小批移除模拟；查看写作包，核对必须采用的结构或模式，映射本项目事实；不适用条目保留拒用原因。
7. **预览候选**：模型模式先查看实际将发送的受审输入，随后检查事实值、条件句、实际引用与保留事项。取消保持报告不变；确认才加入 Plate。
8. **编辑**：使用标题、正文、表格、链接与事实 token 完善报告；保存前预览变化，保存后可刷新与比较版本。
9. **核对导出**：查看问题与引用，绑定当前事实修订的本项目原件，完成核对；通过闸门后导出，未通过时可在许可范围内输出预审稿。

### 5.2 事实变更后的处理

选择事实 → 修改值 → 查看下游规则和已引用段落的影响 → 取消或确认 → 报告标出旧引用 → 更新正文与引用 → 保存 → 为新修订核对证据 → 重新核对报告 → 导出新版本。

当前可确定性定位显式绑定的事实和规则引用。自由文字中的全部语义影响尚不能自动识别，不能承诺“改一处全篇自动正确”。

### 5.3 历史资料浏览

选择澄岳项目 → 七组资料 → 30 类 → 业务记录或文件 → 详情、作用说明、关联图谱或原文。历史语料保持只读；该项目另有“文章写作”，可将所选历史章节的原文切块交给已配置模型，预览后确认保存项目自己的专题工作稿。新项目仍显示文件、事实、规则和报告写作入口，两条写作路径使用不同的事实与交付边界。

## 6. 功能需求与验收标准

优先级：P0 为当前闭环必须保持；P1 为下一轮增强；P2 为具备真实场景后再实施。详细排期、依赖与完成证据以[开发清单](开发清单.md)为准。

### 6.1 项目与资料

| ID | 需求 | 优先级 | 当前状态与验收条件 |
|---|---|---|---|
| PRD-01 | 创建、切换项目和恢复工作位置 | P0 | 已实现。新项目无历史事实；刷新保留当前项目、入口与所选报告；错误有重试入口 |
| PRD-02 | 上传与查看本项目 PDF/DOCX | P0 | 已实现。单文件最大 30 MB，同项目重复摘要拒绝；原文与位置可查看、原件可打开；失败有明确原因 |
| PRD-02A | 普通项目资料总览 | P0 | 已实现限定流程。汇总本项目原件、解析段落与事实；文件跳转到实际内容，事实详情回查原文或规则；真正无资料才显示空状态。不会复制澄岳 30 类历史资产，也不声称普通项目已生成 30 类结构 |
| PRD-03 | 按页抽取事实候选与识别扫描页 | P0 | 部分实现。文本与表格候选、按页请求及扫描页 OCR 已接入；复杂布局、跨页表格与整篇语义召回质量待验证 |
| PRD-04 | 候选审核入台账 | P0 | 已实现。编辑字段和值、主来源及最多两个同页补充来源，确认或拒绝；主来源必须词面支持值；抽取候选不能自动变事实 |
| PRD-05 | 通用语料抽取、校对与发布 | P1 | 待开发。当前只冻结导入澄岳 30 类，没有通用自动抽取 30 类或语料发布工作台 |

抽取质量不得用“请求成功率”替代。后续评价须同时记录漏抽、误抽、字段/值/单位/主语/时点的支持度和人工修改量。当前来源检查以位置与词面为主，语义误配仍需人工发现。

### 6.2 项目事实与规则

| ID | 需求 | 优先级 | 当前状态与验收条件 |
|---|---|---|---|
| PRD-06 | 事实查看、搜索、创建和改值 | P0 | 已实现。值、类型、单位、口径、时点、来源、状态与修订可查；列表保留主要字段，其余在详情 |
| PRD-07 | 确定性计算 | P0 | 已实现。Decimal 与受限表达式支持四则运算、比较、min/max、floor/ceil；循环、除零、单位不一致拒绝；不执行任意代码 |
| PRD-08 | 变更预览与原子提交 | P0 | 已实现。预览列出事实、计算依据与已绑定报告影响；取消零变更；确认校验项目版本与凭证，原子保存修订 |
| PRD-09 | 当前修订的原件绑定 | P0 | 已实现。原始事实绑定本项目片段；计算事实从项目规则与输入来源回链；改值后旧绑定不能替代新修订核对 |
| PRD-10 | 规则生命周期与通用单位体系 | P1 | 部分实现。当前可创建规则并在段落保存表达式及输入修订；项目内字段/规则/章节配置已可试算后发布；改版审批、单位库与自动换算待开发 |

任何形式的未定义值不得被 UI、模型或导出器转换为 0。单位作者须显式表达转换，平台不猜测“万元”和“元”等换算意图。

### 6.4 章节写作包和起草

| ID | 需求 | 优先级 | 当前状态与验收条件 |

## 8. 关键业务约束

### 8.1 历史与新项目隔离

- 选择历史语料只授予特定版本的只读参考范围，不复制历史供应商、金额、需求数值、条件句或审核结果。
- 不适用的报告类型须拒绝套用；新类型应有自己的测试与领域配置。
- 历史证据目录和摘录可以说明当时来源，不能证明本项目当前事实。
- 11/12 项历史内部证据没有完整原件；49 个模板缺少关键覆盖配置；历史 `pass_with_notes` 不能成为新报告的正式许可。

### 8.2 引用和可追溯性

报告段落使用历史记录时须能回查 `corpus_id`、版本、`category_id`、`artifact_id`、`record_id` 和来源位置；事实引用须回查 `project_id`、事实 key、修订及证据；计算段落还须保留项目规则和输入修订。

当前写作包段落已保存这些来源，计算规则以规则 ID、表达式和输入修订快照表达；项目内规则配置版本已可发布；通用论断/证据行内引用与配置审批仍属后续需求。

### 8.3 闸门的用户语义

| 情形 | 工作稿 | 预审导出 | 正式导出 |
|---|---|---|---|
| 尚未人工核对 | 可保存 | 标记状态与问题 | 阻断 |
| 当前事实修订缺少本项目原文绑定 | 可保存，问题可见 | 标记缺证 | 阻断 |
| 关键计算缺依赖 | 可记录缺口；拒绝确定性章节候选 | 只输出已知内容及缺口 | 不能以猜测结果放行 |
| X001 关键冲突未解决 | 可保存披露 | 保留两端来源和未解决状态 | 阻断 |
| 事实引用已过时 | 可保存待更新稿 | 保留问题 | 更新、重新绑定证据和核对前阻断 |
| 模型新增无来源确定性数字 | 可保存待审内容 | 保留问题 | 当前数字/引用闸门不得静默放行 |
| 来源位置已核对、引用与修订一致 | 可保存 | 可导出 | 还须人工核对且无其他阻断项 |

当前数字检查不能自动证明主语、口径、因果和业务结论正确；不得用它取代专业审核。通用关键/非关键分类、行业豁免与审批机制尚未实现。

## 9. 界面与操作要求

- 中文浅色后台，窄白侧栏、浅灰背景、白色内容区、细边框、紧凑表格、蓝色主操作；只显示实际可用入口。
- 主流程入口为“项目文件 → 项目事实 → 规则计算 → 报告写作”；报告页内按“起草 → 编辑 → 核对导出”组织操作。
- 不在页面铺设原理说明、开发说明和重复提示。列表优先展示名称、值、状态与操作，扩展字段放入详情。
- 保留完成操作所需的短标签、错误原因、冲突/缺证状态和导出阻断项；这些是用户决策信息。
- 作用说明通过用户主动点击查看。原始 YAML/JSON 只作为追溯入口，不充当业务主界面。
- 报告页的“资料应用”默认收起；用途、使用方式与模拟结果在需要时展开。配置保存后清空先前审核选择与候选，避免旧配置下的草稿继续确认。
- 候选与工作稿区分；确认按钮具有明确副作用，取消返回原状态；按钮必须有对应实现与反馈。
- 图谱默认显示有意义的局部范围，避免一次铺满全部关系；列表始终保留，状态不能仅依赖颜色。
- 桌面与较窄屏幕均可完成主要任务。当前 500 px 报告页已做真实检查，整站移动端无障碍合规仍待专项验证。

## 10. 数据、安全与运行要求

### 10.1 当前运行边界

开发服务默认只监听本机，数据库端口同样限制本机访问。当前没有登录，因此不应将现版本直接开放给多人网络使用。模型调用仅使用操作者配置的端点；安装依赖可能需要网络，不宣称已有离线安装包。

历史语料原件与解析记录均已入 PostgreSQL。新项目上传原件当前保存在应用存储目录，数据库保存归属、摘要、位置和业务记录；这是两类数据的不同实现，不能宣称所有运行数据都已作为数据库二进制保存。

### 10.2 凭据与发布

模型密钥只在服务端加密保存，接口只显示掩码。运行密钥、模型配置、数据库备份、上传原件、用户项目数据与日志不得提交源码仓库。示例配置不得含真实端点凭据。报告审计不得包含 API Key。

### 10.3 持久化和恢复

事实与报告提交须使用版本检查，防止旧预览覆盖新状态。数据升级前备份数据库；完整恢复还需上传文件存储和必要的服务配置。当前提供人工备份/恢复方法，自动备份策略与生产恢复演练仍待实现。

所有会重建表或写入测试数据的自动化必须连接并断言 `report_platform_test`；禁止将验收重置操作指向应用数据库。

### 10.4 性能与可靠性

当前只承诺已测样本范围。百页报告、万级正文块、批量 OCR、并发用户、导出耗时和恢复时间尚无性能达标结论。后续先冻结硬件、样本规模与用户可接受等待时间，再建立压测门槛；不写未经实测的服务等级。

### 项目内可发布的推演与章节配置（NEXT-20）

项目的“报告写作 → 规则与章节配置”支持建立草稿，配置输入/计算字段、单位与分组、受限表达式规则，以及每章要展示的指标。用户先录入样例值试算，确认计算成功后发布版本。发布版本只读；修改时创建新版本。方案只能显式选择本项目已发布配置，默认不复制任何历史数值。每次运行固定配置 ID、版本、摘要、规则和章节范围；旧方案、运行及报告不会因新版本发布而改变。

报告工作台按所选运行展示配置的可用章节。用户可以预览确定性候选，取消不入稿，确认后在 Plate 中编辑；段落与结果表格保留运行引用。输入为空时显示不可评估，0 为有效输入，循环、除零和单位错误在试算时阻止发布。自定义字段分组与结果列表均按配置显示，不能因为采用新的行业名称而变成空白。

这一能力解决“先建立本项目的字段、规则、章节，再按版本推演写作”的基础流程。章节现可配置必要项目原件证据、受限比较条件的双向文字与模型禁用表述；这些条件在运行中冻结。证据核对且条件可评估时，可发起真实文本模型起草，候选逐段采用。行业论证模板、配置级审批和任意章节通用模型质量仍未证明。合成销售案例仅验证计算链；独立非可研报告样本验证的是显式配置的两章，不代表事故报告全篇完成。具体见[非可研验收](非可研条件证据写作验收_2026-09-26.md)。

## 2026-09-27 增补：新项目从原件到报告的操作收敛（NEXT-25）

全新普通项目应从空事实台账进入，首页直接提供原件上传。用户可按文件名筛选、在已保存的原文片段中搜索、跳至页码和片段，刷新后保留位置。待审页和候选应能连续处理；无数据状态给出可点击的下一步。事实录入默认生成稳定字段 key；可按事实状态筛选，查看来源审核状态，已绑定来源再次打开回到原页。项目资料内的事实来源可直达应用中的原文位置。报告列表可按标题与核对状态筛选，状态必须与导出闸门一致：已人工核对且仅有披露性备注的情景分析可显示为已核对，存在阻断项不能如此显示。事实抽屉具备明确的对话框语义及 Esc 关闭操作。

方案运行须冻结创建时与输入吻合的项目事实修订。用户主动改方案输入造成的差异应作为方案假设披露；后续项目事实变更造成旧运行与当前事实不一致，应阻断旧运行的核对与交付。模型起草仍要求本章证据已核实，不能将方案假设冒充已核实来源。正式事实稿继续按假设边界阻断。

上述操作对应验收记录中的 UX-01 至 UX-21。已核对的情景分析仍须在列表和工作台以短状态标出方案假设；确定性候选不得将“结论待核对”写死在正文，避免核对后自相矛盾。205 页北京可研原件只验证已配置的面积与投资两章，不能推出全类型自动抽取或自动撰写能力。待实现事项沿用 NEXT-02、NEXT-21、NEXT-22：独立专业金标、复杂 Plate 引用迁移、长任务和大规模检索性能。

## 2026-09-27 增补：可研样本的章节候选与交付依据（NEXT-26）

以北京交通枢纽公开可研的建筑面积核对、投资摘录两章作为固定案例。用户选择报告采用的方案运行后，生成面板应显示方案名称与运行修订，可按需展开本章结果；候选正文、结果表和模型段落分别可读、可逐项采用或取消，并能从候选打开所引用的结果详情。取消不改变报告版本。打开面板时，章节目录仍可操作，Plate 正文不得被挤成窄列；较窄屏幕使用单独的上下文抽屉。

模型只接收本章已筛选的运行值、已核对来源和批准条件句。输出缺少结果引用、出现来源外数字或失效条件句时不得入稿；格式错误可自动再尝试一次，仍不合格则明确报错。成功候选仍须人工选择与核对，不因真实模型调用成功而成为正式结论。

情景分析 DOCX/PDF 应让接收人直接看到正文所引用结果的上游输入、规则和代入值，标明“项目事实快照 / 历史参考 / 方案假设”。未引用指标不进入人类可读依据页；完整运行快照仍保留在审计 JSON。北京两章 PDF 不应因新增依据留下仅一行文字的孤页。此需求只验证两章的可用性和导出保真，可研其他专业章节与跨项目写作质量仍待独立金标。

导出格式变更后，同一已核对报告再次交付应得到新版排版，旧交付仍可按历史记录下载原文件；同一格式的重复下载不能产生多份无差别记录。格式身份须进入审计水位，不通过覆盖旧 ZIP 来实现升级。
