## 一、目标与判断标准

本阶段的核心任务是让用户能够：

**打开报告 → 修改方案输入 → 运行推演 → 查看和比较结果 → 选择写作依据 → 生成章节候选 → 在 Plate 编辑 → 处理数据变化 → 核对与导出。**

写作过程中也能重复进行这一循环。用户修改需求量、生产参数或供应商后，应当看到哪些计算结果和判断发生变化、哪些章节需要更新，选择接受哪些变化，并保留自己的编辑成果。

以这条流程作为功能取舍依据。每个新增功能都要回答：用户在什么时刻使用它，它解决哪个具体问题，完成后得到什么结果。与这条流程无关的功能暂缓。

本轮按正式产品的交互、持久化、错误处理、版本与数据可靠性要求开发。部署范围继续采用既定的本机/私有化单用户形态，暂不增加登录、团队协作、收费、多租户或新的模型基础设施。不要据此宣称已经满足对公网生产服务开放的要求。

## 三、统一业务模型：事实、方案、运行与正文

至少明确以下对象，具体表名可以遵循现有代码习惯：

| 对象 | 含义 | 关键规则 |
|---|---|---|
| 项目事实及修订 | 已登记的本项目数据 | 保留来源、口径、单位、时点和审核状态 |
| 方案及输入修订 | 用于分析的一组可编辑输入和假设 | 修改方案不自动修改项目事实或历史语料 |
| 规则修订 | 本次计算所采用的表达式、单位及适用条件 | 已被运行引用的版本不得原地改写 |
| 推演运行 | 某个输入修订对应的确定性计算结果 | 固定输入、规则、精度、结果、状态及追溯；运行完成后不可变 |
| 写作候选 | 根据选定运行和资料产生的建议正文 | 尚未进入报告，可以取消或逐项采用 |
| 报告工作稿及版本 | 用户正在编辑和保存的正文 | 绑定明确的计算运行与来源，保留人工修改 |
| 核对及导出记录 | 某一报告快照的检查与交付结果 | 后续改数据不能覆盖旧记录和旧导出 |

所有对象具有稳定 ID 和明确的项目归属，服务端验证关联对象属于当前项目或明确授权的只读语料版本。禁止靠前端选中状态来保证数据隔离。

方案至少支持创建、命名、复制、编辑、保存与选择。默认以一个基准方案开始，用户需要时再创建其他方案，不强迫用户先填复杂配置。

普通新项目的初始事实仍为空。可以从用户明确选择的当前项目事实快照建立方案；此后项目事实变化，提示方案基线变化，由用户决定更新。不能偷偷改变已经完成的运行。

澄岳项目保留其历史资产不变。用户可点击“新建方案”，选择并确认从澄岳历史输入建立方案副本；原始来源、历史属性、未核实状态必须保留。随后修改副本开展分析。这些值属于历史复演或方案假设，不得自动转成已核实的当前事实。已有澄岳文章应能在统一工作台中打开，旧版本正常保留。

不必为本轮增加新的“假设自动转正式事实”功能；需要维护项目事实时沿用已有的事实修改、预览、确认和审计流程。

## 四、输入数据：先改得清楚，再算得可靠

在写作工作台提供“输入数据”入口，按当前章节筛选相关输入，并允许切换查看本方案全部输入。

1. 按业务含义分组，例如需求、产能参数、设备与供应商。默认显示名称、当前值、单位、必要状态；来源、口径、时点、历史值及修订在点击后展开。
2. 根据字段类型使用合适的数字、文本、日期、选择控件，支持键盘连续录入。能一次修改多个输入，再统一预览计算。
3. 显式区分“项目事实”“历史参考”“方案假设”“计算结果”。历史来源不得因为复制到方案而升级审核状态。
4. 输入空白、有效零值和计算不可评估具有不同状态。清空数值不能变成 0；未知报价不能显示为免费或 0 元。
5. 计算结果默认为只读，点击可看上游输入与公式。修改结果应通过上游输入或明确的规则变更实现，不能允许覆盖一个数值却继续伪装为原规则输出。
6. 数值范围、单位、比例口径与日期错误在字段附近显示可处理的短提示。比例输入需明确显示百分比或小数形式，避免 90 与 0.9 混用。
7. “预览推演”只计算临时结果，取消不保存输入、运行或报告。用户明确点击“保存方案”时可以写方案修订，但不得连带提交项目事实或改写正文。
8. 对保存方案、保存运行、应用到报告分别定义事务和版本检查。测试中的“取消无变更”应检查相应业务对象，不能把必要的取消审计误判为业务提交。

从数据库中的节点与规则记录建立经审核的输入定义及映射。不能从任意 YAML 或原文直接执行表达式。字段、依赖和章节覆盖尽量由版本化配置承载，避免业务逻辑散落在组件中。

## 五、推演：保存运行、比较结果、解释变化

继续使用后端 Decimal 与受限规则引擎，模型不负责计算。

### 5.1 推演能力

- 支持已有四则运算、比较、min/max、floor/ceil及规则依赖，拓扑排序，明确检测循环、除零、单位不匹配和缺失输入。
- 使用明确的单位维度及精度策略。对“产线 × 天数 × 班次 × 工时 × 速度 × 可用率 × 合格率”等链条检查各参数的业务口径；不能通过把单位全部清空来让运算通过。
- 不支持的单位换算应明确报错。需要换算时实现限定、可测试的显式转换，避免无依据自动推测。
- 输入发生变化时重算下游结果和判定。计算公式、适用条件与文字条件分别有记录，条件不成立的历史语句不能继续进入正文。
- 冲突与未知值影响到的结果显示“待核实”或“不可评估”；独立且可计算的结果可以保留，但本次运行的状态必须准确反映局部问题。
- 运行失败或存在阻断时，不能半提交一组被标成已核对的结果，也不能继续使用上一轮结果冒充本次成功。

### 5.2 运行快照

保存运行至少固定：项目、方案及修订、输入值及其来源修订、规则版本与表达式、计算精度、输出与单位、条件判断、缺口与冲突、逐步轨迹、输入摘要和运行时间。

输入、规则、字段定义或舍入策略改变时，产生新运行。报告引用具体 `run_id` 和结果 ID，不能只引用“方案当前值”。重复保存或网络重试应幂等。

### 5.3 结果界面

点击“推演结果”后展示：

1. 少量本章关键结果，例如需求、合格能力、计划销售量与缺口。
2. 输入与输出对比表：基准值、当前值、变化量、必要单位与状态。
3. 判断变化，例如“需求受限”变为“产能受限”，并定位受影响章节。
4. 点击某个结果打开公式、代入值、上游、来源与中文计算过程；必要时打开局部依赖图。
5. 两到三套方案并排比较，可选择用于当前报告的运行。差异率的基准为 0 时显示不适用，不出现无穷大或 NaN。

默认使用清楚的数值和表格，不为了视觉效果堆积图表。资料类别移除实验保留在资料配置的次级入口，使用明确名称，避免和业务方案比较混淆。

## 六、写作工作台：正文始终是中心

先给出简洁的页面草图或组件结构，随后直接实施。应实现报告列表与报告编辑工作台的分离，并复用同一套工作台承载澄岳和普通项目。

### 6.1 报告列表

默认只展示标题、更新时间、当前状态、所用方案和必要操作。“新建报告”打开对话框；不在列表上同时展开创建表单、全部文章内容和模型输入。

### 6.2 编辑工作台

- 顶部：报告标题、保存状态、当前采用的方案/运行，以及简洁的常用操作。
- 左侧：可折叠章节目录，支持定位、增加、重命名和调整章节顺序；调整时稳定 ID 和引用不丢失。
- 中间：主要空间留给 Plate 正文，宽度适合长文阅读，具有标题、段落、表格和引用的清楚层级。
- 右侧：默认关闭的上下文面板。点击“输入数据”“推演结果”“资料”“检查”等入口打开相应内容；同一时刻只保留一个主要面板。
- “版本”“导出”等低频动作可以放在更多菜单中。工具栏不要堆满技术按钮，核心操作要可发现、有文字或无障碍名称。
- “生成本章”作用于当前章节，候选在侧栏或有控制的对照视图中展示，确认后才更新正文。

较复杂的输入表格和多方案对比可切换为专用全屏面板；关闭时恢复原章节、光标/选择和滚动位置，不能回到报告首页。

延续简洁中文浅色风格：白色窄侧栏、浅灰背景、细边框内容区、蓝色主操作、克制状态标签。统一字号、间距、控件高度和表格密度，去掉大面积介绍卡、重复标题和装饰性仪表盘。重视正文阅读与编辑，不将写作区域做成表单后台的附属卡片。

### 6.3 按需展示原则

默认页面不出现教程、实现说明、技术架构、长段注意事项、原始 JSON/YAML、内部 ID 列表或全部来源卡片。

必要的字段标签、单位、保存状态、冲突标记、错误与下一步操作必须保留。把帮助、公式、来源、完整审计和资料作用放在按钮、弹层或抽屉内；不要为了简洁而隐藏会影响用户决策的错误。

资料的“作用”按钮点击后显示该资料在当前章节的实际用途、采用记录、相关输入/段落以及未采用原因。关闭后恢复简洁页面，不自动铺开 30 类说明。

对现有主要页面进行同一原则的检查：

| 页面 | 默认显示 | 点击后显示 |
|---|---|---|
| 项目与报告列表 | 名称、状态、最近修改和主要操作 | 新建表单、详情和历史 |
| 项目事实/方案输入 | 筛选后的字段、值、单位和必要状态 | 来源、口径、修订和影响 |
| 规则 | 名称、目标、计算状态 | 表达式、依赖图、测试输入和版本 |
| 项目资料 | 分组、类别及当前记录列表 | 记录详情、作用、原文和图谱 |
| 写作工作台 | 章节目录、正文、保存状态和少量操作 | 输入、推演结果、来源、候选、检查和版本 |
| 模型配置 | 名称、用途和连接状态 | 编辑、连接测试和高级参数 |

禁止用简单地给原来所有卡片套折叠框来代替任务组织；用户应能判断下一步点击哪个动作，并在完成后回到原上下文。

### 6.4 操作习惯与可用性

- 有真实路由或等效可恢复地址，刷新与浏览器前进后退能够保持项目、报告和章节，不仅依赖内存状态。
- 编辑正文采用自动保存工作稿或直接保存，提供 Cmd/Ctrl+S；普通文字编辑不再每次都经历“预览—确认”两次操作。
- 自动保存只保存工作稿，不自动通过核对、不自动接受候选、不自动切换计算依据。形成清晰的“保存中 / 已保存 / 保存失败”状态及版本冲突处理。
- 中文输入法组合期间不能触发破坏性保存、重置选择或跳动光标。撤销重做和复制粘贴符合常用编辑器习惯。
- 未保存输入关闭时给出保留或放弃选择；已自动保存的正文不得反复弹确认框。
- 面板支持关闭、Esc、焦点恢复和键盘操作。窄屏只显示正文或当前面板，避免挤成三列或页面整体横向溢出。
- 网络错误、无数据、模型不可用和权限/归属错误均有准确状态；重试不能重复创建章节或运行。

## 七、让推演结果真正成为写作依据

### 7.1 组装写作输入

用户选择一份有效运行后，从数据库组织当前章节写作包：

- 当前方案的输入、假设和明确选定的运行结果。
- 实际采用的规则版本、计算条件、来源与修订。
- 经审核适用的结构、模板、术语、写法和论断约束。
- 能支持当前内容的证据、摘录，以及必须披露的冲突与缺口。

每条记录具有项目、方案/运行或语料版本等身份。分开记录历史原文、当前事实、方案假设、计算结果和模型表述的来源，不把历史引用当作新数值的证据。

旧供应商、报价和条件句不得混入新输入。模型只收到本章需要且允许使用的内容。继续使用现有模型配置中的文本模型，不新增写死的模型地址或密钥。

模型输入在用户点击“起草依据”时可以核对，但不要求每次常规操作都展开大段技术内容。输入改变后，旧候选应失效或明确标为过期，不能偷偷切换依据。

### 7.2 候选与采用

- 基于选定运行生成正文候选，并以确定性方式生成需要的结果表格及数值引用。
- 每段候选可查看依据、保留事项和是否需要人工核对。支持采用本章、按段采用、取消与重新生成。
- 替换已有章节前展示受影响范围。未选中的章节和人工编辑内容不得被覆盖；同一候选重复提交不会重复插入。
- 模型不允许自编计算值或把预测需求称为订单。数字校验基于对应事实或运行结果及约定显示格式，不能只检查数字是否在某处历史原文中出现过。
- 区分业务数值、章节/表格编号、日期和标准条号；年份或表序号不能误绑定为计算结果。展示格式与精度转换可核对，不能依赖“数字集合相同”判定整段语义正确。
- 模型不可用时保留手工写作和确定性结果插入能力，明确显示模型状态。不能用固定拼接文本冒充模型成功响应。
- 生成、取消、拒用、采用与人工修改有可检查状态和必要审计，密钥不进入提示词、日志或导出。

### 7.3 范围与配置

将章节需要的输入、规则、表格、允许的判断和核对要求放入可版本化配置。首批以澄岳可核实内容完成多章节写作，既有 S4、S5.2、S7.1 作为回归入口，并选择至少一个有充分依据的新增章节验证配置扩展。

新增章节是否开放由输入和证据决定；若某章无法支持，应记录缺少的内容并保留缺口，不虚构数据完成章数。用合成测试验证通用配置引擎，不把合成案例当真实业务证据。

不能宣称所有 49 个历史模板都能直接生成，也不能将可研规则自动应用到其他类型报告。

## 八、Plate 与数据的双向操作

沿用现有 Plate，完成本轮真实使用所需的章节、正文、列表、表格、链接、引用、斜杠菜单、撤销重做、粘贴、保存、版本和导出。

1. 正文事实引用与计算引用区分类型。计算引用至少绑定方案、运行、结果 ID 和显示规则；段落和表格保留稳定 ID。
2. 点击数字或引用打开对应输入、公式及来源；从输入、结果、规则、冲突也能定位相关章节和段落。
3. 新增 Plate 属性或节点同时覆盖前端编辑、序列化、后端校验、数据库、版本差异、复制粘贴、拆分合并和 DOCX/PDF 导出。未知类型不得静默丢弃。
4. 表格中的结果单元格同样能够追溯；不能仅把有来源的结果变成普通字符串后丢失绑定。
5. 修改方案不会立即覆盖正文。新运行产生后，在“检查”中列出旧值、新值、变化判断和受影响位置，用户选择更新。
6. 明确分开“更新绑定数值”“更新结果表格”和“重写条件相关段落”。数值替换不能被当作逻辑已重新核对。
7. 用户手工改写已绑定的数字或判断时，提示解除/重绑或形成待审核提议；不能静默回写事实，也不能保留虚假的旧核对标记。自由正文的语义识别若未实现，应准确说明边界。
8. 尽量保留用户格式、非关联段落及已经接受的人工修改；可能冲突的改动用局部对照处理。
9. 报告默认选用一套主运行。确需对比多个方案时，使用明确标注方案的对比段落/表格，不允许同一指标在普通正文里无提示混用不同运行。

## 九、30 类资料的应用方式

保留数据库中的完整历史资产及 30 类内容化预览。用户写作时看到的是相关资料与作用，类别编号和文件名放在详情中。

为每类配置本章的“参与起草 / 仅供核对 / 不使用”等策略，并保留记录级实际采用与拒用理由。原有兼容接口可保留，用户文案应能直接理解。

至少区分以下作用：

- 节点与规则：输入定义、计算依赖及结果来源。
- 章节、骨架与模板：文章结构与可复用写法，须重新校验适用条件。
- 论断、证据与摘录：约束结论和提供回链；证据缺失保持可见。
- 冲突、缺口与校验：影响判断和导出检查。
- 文风与术语：受控地影响表述。
- 清单、位置映射、索引与追踪：定位、核对或审计支撑，不强制进入模型上下文。
- 向量与签名：未生成的部分继续标明未生成，不作为本轮已具备的能力。

每类的作用按钮应显示“当前实际用于哪里”，没有采用就如实显示未采用。进入模型上下文、出现在来源列表、实际影响正文是不同事件，分别记录。不要为了凑 30 类调用次数制造虚假使用记录。

## 十、核对、导出与任务可靠性

报告状态区分工作稿、待核对、已核对与可交付；候选独立于报告正文。已核对状态绑定精确内容、输入、规则、运行和证据水位。

- 阻断项要能点击定位并处理，普通页面只显示必要数量和短状态。
- 分开评估“基于明确假设的情景分析”和“对现实项目的确定性结论”。允许用户交付经过核对、假设与限制清楚的情景分析；不能把假设升级为已证实事实。
- 无依据确定性数字、过时引用、未经核对模型判断和未披露关键冲突不能静默放行。
- 预审稿、情景分析报告和正式事实结论的导出规则应明确，文档、界面和审计命名一致。不要通过隐藏问题或更改标签绕过检查。
- 导出固定报告版本与运行，包含正文、结果表格、必要引用和保留事项；审计记录包含同一水位的输入、规则和模型使用摘要。
- 导出后修改方案或报告不改变旧文件；导出失败不能显示已成功。

模型生成和较长导出采用可查询的任务状态，处理刷新、超时、取消和幂等重试。优先使用当前技术栈和数据库完成本轮所需的可靠性，不为此引入无关的大型调度平台。

## 十一、先固定以下业务验收案例

在实现前登记输入、预期结果和失败条件，不能开发后再挑成功案例。

### A. 需求与销售

- 输入需求 300,000 套、合格能力 254,016 套，`min` 得计划销售量 254,016 套；若配置差额指标，则为 45,984 套。正文表达产能约束，不能残留“需求低于能力”。
- 需求改为 200,000 套，销售为 200,000 套；判断和正文条件相应改变。
- 需求为 0，销售为 0，显示有效结果。
- 需求缺失，销售不可评估，不使用 0 或上次结果替代。
- 需求等于能力时按边界条件表述，不能误判为严格大于或小于。

### B. 从参数计算产能

建立明确口径的验收链：2 条产线 × 300 天/年 × 2 班/天 × 8 小时/班 × 30 套/小时 × 90% 可用率 × 98% 合格率，经规定取整得到 254,016 套/年。

将天数改为 250，其他输入不变，得到 211,680 套/年；需求仍为 300,000 时，计划销售量变为 211,680，差额 88,320。用户能够从结果查看完整代入过程、比较前后结果并更新相关正文和表格。

这些数值是预先固定的验收输入。即使与历史记录一致，也必须逐项核对映射，不能把测试参数冒称为已核实的新项目资料。显式规定年度数量和“套/年”口径如何对应。

### C. 供应商与报价

从历史方案复制后，将供应商改为“新供应商甲”。没有新报价依据时，候选不能残留“禾进装备”、历史报价区间、无条件采购建议或旧限定语。相关价格与判断保持待补；用户可查看需要补什么来源。

### D. 配电冲突

X001 的 800 kW 与 650 kW 及其两个来源保持未解决状态。可分别建立“采用来源 A 数值的假设”“采用来源 B 数值的假设”进行条件分析，但不能把分支选择当成已裁决冲突。没有完整适配依据时，禁止确定性适配结论和无条件采购建议。

### E. 论断与证据

L002 的“需求不是订单”约束实际影响生成；EV-01、支撑节点及原文可回链，独立核实状态可见。没有订单证据不能生成已签订单结论。

### F. 版本、编辑和导出

保留一份基准报告，改方案生成新运行。旧报告仍能查看原来的输入、计算和正文；新结果提示待更新。选择更新一章后，其他章节和人工修改保留。重新核对与导出后，文件、表格和审计全部绑定新运行。

### G. 报告类型边界

选现有非可研公开报告作为负例：可以使用通用编辑与方案基础能力，但不能自动继承澄岳的行业章节、供应商、证据和计算规则。

### H. 操作失败与恢复

预览后取消、模型返回失败、规则循环、除零、单位错误、并发修订、重复点击提交、切换项目后旧请求返回、刷新页面和服务重启，均不能损坏已有数据、重复入稿或显示错误的成功状态。

## 十二、分阶段实施，逐段验证

将以下任务加入现有开发清单，分配稳定 ID，标明依赖与真实完成状态。不要仅修改状态文字。

1. **方案与运行基础**：非破坏迁移、输入修订、规则修订、只读历史副本、运行快照和版本检查。先验证数据保护与基本计算。
2. **输入与结果界面**：可编辑输入、推演、保存、方案对比、计算详情与作用范围。先让用户能完整改数据并核对结果。
3. **写作工作台**：拆分列表/编辑器，章节目录，按需面板，保存和路由恢复；保留旧文章可编辑。
4. **运行驱动写作**：写作包、模型候选、结果表格、稳定引用、逐段采用与取消。完成真实模型调用。
5. **修改后联动**：结果与正文影响、局部更新、人工修改保护、重新核对、固定版本导出。
6. **全流程验收与文档**：真实浏览器、窄屏、故障恢复、导出解析、迁移恢复验证及 PRD/设计/清单更新。

每段完成对应测试并修复，再进入依赖它的下一段。发现现有代码不支持关键设计时，先完成必要重构；不以增加更多布尔分支来长期维护两套不一致的写作流程。

## 十三、测试要求

所有会重建表或写测试数据的自动化测试，必须连接并执行前断言 `report_platform_test`，不要与其他重建测试并发。日常数据库只进行明确的迁移和用户授权的持久操作，不拿现有项目跑破坏性测试。

后端至少覆盖：

- 历史资产及旧文章保护、迁移兼容、归属校验。
- 方案复制、输入修订、Decimal、比例口径、精度、单位、0/缺失、循环和除零。
- 运行不可变、预览取消、事务回滚、重复请求幂等、版本冲突。
- 写作输入快照、候选过期、来源类型校验、条件句变化及历史内容残留。
- 引用影响、报告采用/替换、核对状态失效、固定版本导出审计。

前端除有针对性的组件/接口测试外，必须使用真实前后端完成：

**打开澄岳 → 新建方案并确认历史副本 → 修改输入 → 预览后取消 → 再推演并保存 → 复制第二方案 → 对比 → 选定运行 → 新建多章节报告 → 生成候选并取消 → 重新生成并采用 → Plate 输入 `/`、插入结果引用、编辑表格 → 保存刷新 → 再改输入 → 处理正文影响 → 核对 → 导出。**

再用全新普通项目验证初始事实为空，同一工作台可用，不自动载入澄岳历史值。

至少测试桌面常用宽度和较窄窗口；面板默认关闭，正文空间足够，按钮真实有效，焦点/返回/刷新正常，无控制台异常。区分使用接口替身的测试和真实后端测试，不能将前者报告为完整端到端通过。

至少一次真实内网文本模型调用完成本次运行驱动的写作。模型暂时不可达时如实登记未通过环节，继续完成独立功能，不能用模拟响应宣称真实链路已通过。

导出要解包检查 DOCX、解析并查看 PDF，核实正文、中文字体、标题、表格、数值、引用、假设和审计一致。不能以文件存在或 HTTP 200 当作导出质量通过。

代码静态检查、构建和针对性回归通过后停止无目的重复测试，将时间用于修复实际用户流程问题。

## 十四、最终交付

交付运行中的统一写作工作台，以及以下可操作成果：

1. 澄岳项目可查看未改变的历史资料，创建并保存业务方案，实际修改输入并计算。
2. 至少两份明确不同的方案及对应运行，可在界面对比并追溯。
3. 一份由选定运行驱动的多章节分析报告，包含推演结果表、条件判断、证据或缺口；Plate 可编辑、刷新保存和查看来源。
4. 一次数据变化引发局部正文更新的真实验证，保留旧版本和人工修改。
5. 经过检查的导出文件及对应审计记录；不足以形成正式结论的部分准确保留限制。
6. 更新的 README、PRD、详细设计、开发清单、数据库升级与恢复说明，以及本轮验收报告。
7. 简短的实际操作步骤：从哪个入口进入、在哪里改输入、如何推演、如何采用结果写作、如何保存与导出。

最终总结逐项说明：本轮真正完成的用户动作、真实测试结果、尚未通过和未覆盖的部分、30 类资料的实际参与范围。不要把“保存了几段模型文字”“页面可打开”或“测试数量增加”当作本轮目标完成。

本轮是否成功，最终以用户能否独立完成“改数据、看推演、选结果、写报告、再改再写、核对导出”，以及日常页面是否保持简洁、清楚、可恢复为准。
