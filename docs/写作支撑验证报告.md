# 澄岳精密 30 类语料的写作支撑验证

验证日期：2026-09-24。对象：只读历史语料 `cy_tray_20260918@v2`，以及新建的合成 QA 项目。本报告评价**已经入库的语料怎样进入实际写作**；不评价这套数据的跨行业抽取准确率。预注册、初轮、修复后 21 组重采集、13 次遮蔽与证据绑定机制结果均留在 `test-fixtures/writing-support/`；批量自动化只对 `report_platform_test` 写入，未重建应用数据库。真实浏览器联调另在应用库中新建 QA 项目和试验稿，保留原有项目与历史语料。澄岳精密是虚构历史语料，QA 输入也不是真实商业证据。

## 结论

当前版本可以在可研/建设类试验中把**两个已验证的历史段落形式**转成有项目事实、有规则版本、有历史来源位置的待审正文，并在 Plate 报告中保存。需求 `300,000` 套、合格能力 `254,016` 套时，项目 `min` 规则产生计划销售量 `254,016` 套；需求为有效值 `0` 时结果为 `0`；需求缺失则拒绝确定性候选。新供应商试验没有残留“禾进装备”或旧报价范围。X001 可形成明确写着不作配电适配结论的预审披露，正式核对与导出被阻断。事故调查类型选择澄岳可研参考返回 409。

这**尚不能证明 30 类都需要成为新项目的固定产物**。本轮 21 次真实 API 实验中，8 类留下了报告正文 `source_refs`，4 类只在工作包可见或被拒用，18 类没有观察到该流程的记录级消费；“没有观察到”不等于不需要，也不能据此删除历史归档。直接遮蔽有些类别只触发固定代码缺项错误，不能把它解释为信息必要性。第 11 类向量仍为零行、未生成。

无项目原件绑定时，修复后的正式 review 返回 400，正式 export 返回 409；预审 ZIP 可以下载，`audit.json` 标明 `delivery_status=preview_only`，记录缺证、冲突和事实修订。另用明确标注为 QA 合成输入的 DOCX 做位置绑定机制实验：两个原始事实分别绑定到原件段落，计算事实通过项目规则和已绑定的输入回链，随后 review/export 均返回 200。正式 ZIP 审计将结果标为 `derived_from_reviewed_inputs`，并记录规则及两段来源。**这只证明软件的位置、词面和计算链闸门能工作，不证明合成资料的外部真实性，也不把历史摘录当作新项目证据。**

### 对新项目固定产物的判断

本轮真正有用的是**信息契约和稳定来源关系**，不是要求每个新项目生成一套同名的 30 份文件。当前三节试验直接消费章节/骨架/论断/冲突等数据库记录；项目事实、项目规则、版本、证据位置和核对状态必须另行建立，不能从历史语料复制。CAT-04、09、10、13、15、18、23、27 在本轮留下来源或风险披露回链，但实验没有证明它们必须作为八种独立文件固定产出。

CAT-11 的向量为空，CAT-30 的向量权重未生成，不应强制新项目产出。CAT-06、17、20、28 可作为从原文、图谱或索引关系重建的展示/检索投影候选；本轮没有观察到独立文件带来写作增益，重建一致性仍需实测。CAT-01、02、03、05、07、22、25 主要用于语料身份、原件位置和过程审计，应该保留必要的原始记录及日志，但不应把历史 gate 结果复制为新项目许可。CAT-08、21、24、26、29 等只有遇到表格、方案取舍、缺口、文风或术语匹配任务时才有验证空间，本轮不能定为每个项目的必产物。这个处置是**当前产品默认值**，后续应以不同报告类型和等价信息替换试验复核。

## 预注册与方法

测试设计在写作包开发前固定于 `test-fixtures/writing-support/cases.json`、`protocol.json`、`human-review.md`。`validate.py` 只读检查通过：7 个案例、30 类、3 种包、关键记录 ID、manifest 与跨类型负例 PDF 摘要均匹配，不调用数据库或模型。初轮原始响应是 `api-capture-initial-test-db.json`；最后重采集为 `api-capture-final-test-db.json`，其汇总是 `api-summary-final-test-db.json`；原 11 次遮蔽在 `api-ablation-test-db.json`，新增 #19/#24 两次在 `api-ablation-review-only-test-db.json`；合成原件闸门实验是 `api-evidence-gate-test-db.json`。`summarize.py` 只从真实 `used_items`、`rejected_items`、段落 `source_refs` 和刷新后的报告生成汇总，对语料版本、类别、资产、记录 ID 做交叉核验：21 次均无身份不一致，所有可判定的预注册技术断言通过；最小包的固定构造器缺项单列为实现耦合，不计通过。

三种工作包：`minimal_information_contract`（既有 8 类核心信息假设）、`applicable_conditional`（加适用条件类）、`all_available`（30 类均可核对，仍不把未生成向量当输入）。每次都从空白 QA 项目起步，以相同合成事实、相同规则表达式和 guided 模式比较。最小包在本实现里因缺少目录、模板或骨架而无法起草；这首先是**实现耦合**，不证明所有未来项目须生成同名文件。适用条件包与全量包在 6 个可比较的案例中，规范化候选文字与问题代码一致；事故负例没有工作包。这个结果只适用于当前两段和冲突披露，不是 30 类的普遍消融结论。

初轮（证据闸门修复前）C0052、C0083 与 L002 即使只有合成事实也能 review/export 200；这会让预审资料看起来像已核对正式稿。修复后上述确定性事实段落没有项目原文绑定时正式阻断，预审仍可下载并标注。X001 从初轮起正式阻断。除预审正文外，预审 ZIP 的 `audit.json` 保存 `writing_issues`、`evidence_bindings`、历史 `source_refs`、项目规则 ID/表达式及输入事实修订。最后重采集检查 DOCX 的完整预审标记和 PDF 文字抽取的规范化标记均为 true；PDF 的 CID 字体会省略装饰性的中点 `·`，首次按字面完全匹配的检查是假阴性。合成原件绑定实验的正式 DOCX/PDF 均含 `254,016`，审计区分两条 `source_locator_reviewed` 输入和一条 `derived_from_reviewed_inputs` 计算结果。

可选模型试验对 S4 三轮实际请求 `mode=model`：前两轮因模型输出未保留可定位事实值而返回 503，报告没有变化；服务端收紧事实键校验后，最后一轮用约 1.296 秒返回 200 的**待审候选**。候选中的三个 `fact_ref` 分别为当前项目的 `300,000`、`254,016`、`254,016`，携带本项目 min 规则与历史回链，保守句没有把需求称为订单。此候选未提交，刷新后报告版本仍为 1；这证明模型路径能产出可核对预览，**未证明模型段落已通过人工编辑与正式导出**。模型句中还保留了括号字段名（如 `first_year_demand`），展示文案需要打磨。guided 模式仍是本轮完成提交、核对和导出的路径。

### 合成原件绑定机制

另建一个空白测试项目，在内存生成并上传明确写着“仅供软件流程验证”的 DOCX。其第 3 段写 `300000` 套、第 4 段写 `254016` 套；项目事实录入后分别绑定到 `d-p3` 和 `d-p4`，两次接口均返回 `SOURCE_LOCATOR_REVIEWED`。直接给计算事实 `planned_sales` 绑定文档位置返回 409，防止把计算值伪装成原文。随后通过同一 S4 guided 写作流程提交，review 和正式 export 均返回 200；正式 ZIP 的 `delivery_status=source_locator_reviewed`，审计里两个原始输入为 `source_locator_reviewed`，结果为 `derived_from_reviewed_inputs`，并列出项目 `min(first_year_demand, qualified_capacity)` 规则 ID、输入修订及文档位置。DOCX 与 PDF 正文都能读到 `254,016`。这个测试只核实平台的核对机制，不能说明合成 DOCX 中的业务陈述真实。
