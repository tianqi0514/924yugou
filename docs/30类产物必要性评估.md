# 澄岳精密 30 类产物的必要性评估

评估日期：2026-09-24。对象是已导入平台的**一个虚构历史语料版本**，不是通用报告的数据模型标准。这里的“必要”指在下一份新项目报告中，为完成可核对的“来源 → 候选 → 项目事实 → 起草 → 核对 → 交付”链路，是否必须保留该类**独立的逻辑信息**；并不指必须继续保存同名 YAML/JSON 文件。当前演示项目的 30 类原始资产仍须完整保留、可查看和下载，不应根据本评估删除历史记录。

## 结论与判定口径

**30 类不应全部成为每个新项目的必填产物。** 建议保留 8 类核心信息契约，15 类按报告内容或所启用能力产生，5 类作为可重建投影，1 类只作历史事件归档，1 类仅记录“尚未生成”的状态。核心信息中的具体记录数可以是零；例如没有识别到证据时，系统要明确表示缺证据，而不是造一条证据。历史语料的可追溯性与新项目的运行时最小模型是两件事。

| 处理级别 | 数量 | 含义 |
|---|---:|---|
| 核心信息 | 8 | 需要有版本、来源、可定位正文、经过审核的事实候选与证据等逻辑契约；可以存在不同表中 |
| 条件性 | 15 | 仅在有章节、表格、规则、关系、冲突、可复用骨架等相应内容或能力时建立 |
| 可推导投影 | 5 | 从权威对象重建；历史快照仍冻结保存，不能用新投影覆盖旧审计结果 |
| 历史归档 | 1 | 事件轨迹按发生时的原样留存，不作为每次写作调用的必需输入 |
| 未生成 | 1 | 当前只有零行占位与状态，不得当作已具备的向量能力 |

“核心”是**信息责任**，不是说每份报告都要产出一份同名文件。比如新项目 PDF 的可定位片段和人工确认事实承担了 #09、#12 的职责，但不需要生成 `chunks.jsonl` 和 `nodes.yaml`。冲突检测与缺口标注应始终可用；只有检测到实例时才有 #23、#24 的记录。每类的“合并/不单存”建议仅针对将来的运行时模型；本版本已经入库的 117 个文件不变。

## 可复核证据

1. 以 `demo-data/澄岳精密/解析产物/manifest.yaml` 为类别及实际路径准绳，以用户提供的 `澄岳精密_30类产物文件位置与意义说明.xlsx` 解释用途。独立脚本对 30 类、114 个产物文件、3 个辅助文件及 `SHA256SUMS` 的 116 项摘要逐一核验，全部一致。脚本不执行包内 `validate_package.py`。
2. 运行 `test-fixtures/corpus-necessity/evaluate.py`，每轮只在内存中遮蔽一个类别，再调用现有的 `writing.source_cases` + `writing.render_cases` 和 `CorpusRepository.graph` 的内存引导分支。基线为 2 个章节候选块，图谱 728 个实体、2,232 条边（1,666 条原始、566 条由明示字段构建）。遮蔽 #09 或 #10 时章节验证不可运行；遮蔽 #04、#09、#12、#13、#14、#15、#18、#23、#24 任一类时当前**图谱构建器**不可运行。逐类结果在 `test-fixtures/corpus-necessity/results.json`。
3. 这只是对**当前两项历史语料功能的代码依赖消融**，不是 30 类对写作质量的因果测量。图谱目前按固定路径组装，某类遮蔽后失败，不能证明它在所有报告领域必须单独存在。反过来，某类遮蔽后当前功能仍可运行，也不能证明它没有审计或业务价值。
4. 普通项目的上传、抽取候选、事实确认、报告起草、Plate 编辑与导出路径不读取这套历史语料的 30 类文件；`backend/app/main.py` 中历史语料的运行时调用集中在项目语料浏览和章节验证。过去公开报告链路只对北京可研、江门环评、晋江事故报告各一页确认过一条事实，并非整篇报告或跨类型领域包验证（见 `test-fixtures/public-reports/baseline-extraction/全链路验证_2026-09-24.md`）。
5. `03-澄岳精密解析产物审查与写作适配建议.md` 对结构一致性、可复用骨架、条件句、冲突、空向量和独立人工复核缺失已有核查；本评估沿用该边界，没有把包内 `pass_with_notes` 当作正式报告许可。

复跑命令（无需数据库、模型或网络）：

```bash
# 在仓库根目录执行
.venv/bin/python test-fixtures/corpus-necessity/evaluate.py
```

脚本运行前将数据库地址设为不可达的本机端口，只读取复制的演示语料，并写入同目录的 `results.json`。

## 逐类处置矩阵

表中“影响”指**若在未来运行时不再独立生成该类**会失去什么，或应从哪个权威对象重建；不是要求删除当前冻结语料。编号和路径与 `manifest.yaml` 一致。

| # | 类别 | 处理 | 依据与合并 / 不单存的影响 |
|---:|---|---|---|
| 01 | `manifest.yaml` | 核心 | 语料身份、版本、来源摘要和 30 类清单是同一次抽取的边界。可改为数据库的不可变版本清单；若连版本与摘要也删掉，页面与审计无法证明记录属于同一批。包内“约束”只作历史数据，不作平台指令。 |
| 02 | `meta.yaml` | 核心 | 项目、报告类型、编制日期等帮助识别来源及适用范围。可合并进项目/源文档元数据；不能把历史项目的规模、地域和值预填新项目。 |
| 03 | `provenance.yaml` | 核心 | 输入指纹、抽取器版本、转换与人工审核状态决定候选能否被信任。运行时保留必要溯源事件；长篇格式转换说明可随历史版本归档。缺少这类信息，难以解释同一原件为何产生不同候选。 |
| 04 | `outline.yaml` | 条件性 | 有章节的报告需要树形导航、章节覆盖和正文定位；短报告或无固定章节的资料不必造 49 级条目。可由带稳定 ID 的章节 AST 与块归属重建；删除后当前图谱构建器和语料章节视图会断。 |
| 05 | `source/original.docx` | 核心 | 冻结原件是复核抽取与交付审计的最终依据。本样本是 Word；通用平台接受 PDF/DOCX 等原件，不要求每个项目必须有 DOCX。只留解析文本会失去版面和原始文件核查能力。 |
| 06 | `source/normalized.md` | 核心 | 可定位的统一正文是切块、摘录和词面核验的基准。可作为带解析器版本和摘要的数据库正文投影，不必独立 Markdown 文件；重跑解析器可能改变偏移，旧引用必须继续指向冻结版本。 |
| 07 | `source/offset_map.json` | 条件性 | 需要精确字符区间回链 Word XML/页码时才需细粒度映射。普通 PDF 页/段级引用可存在片段定位字段；不保留细粒度映射会失去本样本的字符级高亮与精确回放。 |
| 08 | `source/assets/*` | 条件性 | 原件确有 18 张表，表格矩阵对数值与行列审核重要；无表的报告不应生成空资产目录。可将表格作为源片段/原件附件存储；只留连成一串的文本会损伤单元格关系。 |
| 09 | `chunks/chunks.jsonl` | 核心 | 194 个带位置的原文块是当前章节验证与图谱回链的直接输入，也是模型候选的核对单元。新项目可存为 `source_segments` 等记录，不必 JSONL；遮蔽它会使本样本章节验证和图谱构建失败。 |
| 10 | `chunks/skeletons.jsonl` | 条件性 | 当前两个章节验证案例直接依赖占位骨架；194 个骨架含 630 处绑定。但“可复用”仍未完成身份、条件和事实审核，不能默认进入通用写作。若产品不用历史表达复用，可不生成；若用，必须保留槽位格式、来源和适用性状态。 |
| 11 | `chunks/embeddings.parquet` | 未生成 | 文件只有 schema 和 `not_generated` 元数据，**0 行向量**。当前靠结构化/关键词能力工作；未来启用语义检索时应以经审核的目标文本重算向量并建版本化索引，不能把本文件当已有检索能力。 |
| 12 | `graph/nodes.yaml` | 核心 | 经来源核对的事实/判断候选是项目事实台账的输入；本样本 339 个节点中只有 201 个实质语义节点，其余含编号与格式信息。可拆为候选、确认事实和文档结构字段；不能把 339 个历史值复制到新项目。遮蔽后当前图谱构建失败。 |

| 14 | `graph/relations.yaml` | 条件性 | 1,666 条有向关系适合多跳影响/证据回链；简单事实到正文的引用可用关联表表达，不必为每份报告生成同规模图。删除关系会使本样本图谱构建失败，跨对象传播也无法复原；不应据此强制每种报告有 1,666 条边。 |
| 15 | `graph/claims.yaml` | 条件性 | 48 条论断把结论与事实、证据、复核条件分开，适合论证型报告；只做资料摘录时可暂不抽论断。若报告要自动检查“结论有依据”，就必须保留同等语义关系；遮蔽后当前图谱构建失败。 |
| 16 | `graph/invariants.yaml` | 条件性 | 18 条是这份可研及抽取包的校验定义，不能当所有专业报告的通用闸门。运行时应把通用安全检查放平台，将领域检查放审核过的领域配置；未配置对应领域时不应硬套投资/面积规则。 |
| 17 | `graph/graph.yaml` | 可推导投影 | 合并快照重复节点、规则、关系等分文件信息。可按语料版本从独立权威对象按需构建局部图；直接删除当前快照会影响本样本第 17 类的历史预览与按字节归档，故仍保留原资产。 |

## 逐类代码与记录的核对入口

上表每一行 `#NN` 都有同一套可直接复核的实现定位：数据库 `corpus_categories.category_id=CAT-NN` 对应 `corpus_records.category_id` 与 `corpus_artifacts.category_id`；接口 `GET /api/projects/{project_id}/corpus/categories/NN` 调用 `CorpusRepository.category(NN)`；前端 `CorpusView.tsx` 的 `CategoryContent` 中有 `number === NN` 的专用分支。`backend/tests/test_corpus_storage.py::test_import_is_complete_repeatable_and_database_only` 在断开语料目录后逐类读取首条记录、稳定记录 ID 和资产 ID；本轮另在浏览器逐项打开 30 类。`test-fixtures/corpus-necessity/results.json` 的 `categories[number=NN]` 保存该类物理文件数与两项遮蔽实验结果。这些入口适用于 01–30 的每一行，避免把同一套调用路径重复写 30 遍。

当前**实际运行时下游调用**只有两组：`writing.source_cases` / `writing.render_cases` 使用 #09、#10 做历史章节验证；`CorpusRepository.graph` 的引导构建路径直接读取 #04、#09、#12、#13、#14、#15、#18、#23、#24。其余类别目前的下游是相应资料浏览/原件核对视图，没有已证实的写作计算消费者。因此，不能把“页面可打开”误当作“写报告必须生成”。数据、代码和测试的交叉索引如下：

| 类别 | 当前下游 | 可复核证据 |
|---|---|---|
| 09、10 | 历史章节验证；09 还用于合并图谱 | `results.json` 对应两行的 `chapter_validation_available=false`；`backend/app/writing.py` 的 `source_cases` 与 `render_cases` |
| 04、12、13、14、15、18、23、24 | 合并图谱构建；相应类别浏览 | `results.json` 对应行的 `graph_builder_available=false`；`backend/app/corpus.py` 的 `graph`、`graph_slice` |

## 下一轮应怎样真正验证“够不够用”

当前消融证明的是代码直接依赖，不是产品必要性或抽取准确率。下一轮应对每种待支持报告类型各取**未参与设计**的完整原件、人工审定的事实/论断/证据及一份新的项目输入，逐层量化：原文与表格定位、事实候选召回与误抽、单位/口径/时点、跨片段证据、规则前向回放、结论支撑、冲突缺口披露、章节覆盖、编辑后引用一致性及导出闸门。先在北京可研、江门环评、晋江事故调查和扫描件上比较最小契约与条件性类别的增益；没有对应内容时应允许该类为空。若某类没有改善可用性、审核效率或审计可解释性，再决定是否不纳入新的运行时模型。

单个澄岳精密样本没有独立人工金标，也没有完整的 11 份内部来源原件，不能据它断言“通用报告只需 8 类”或“30 类均可自动准确抽取”。本评估给出的是当前系统的**合理最小结构假设和可复核取舍**。
