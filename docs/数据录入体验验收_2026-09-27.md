## 固定案例

| 动作 | 预期 | 失败条件 |
| --- | --- | --- |
| 新建整数事实“首年需求”，值为 `0` | 一次保存为 `PROVIDED`、`r1`，记录来源和首条修订 | 被当作未定义，或只建字段未保存值 |
| 新建无值的计算目标 | 保存为 `UNDEFINED`、`r0`，随后可作为规则目标 | 错写为 0，或自动生成假结果 |
| 输入 `1.5` 到整数事实 | 返回明确错误，项目版本和事实行不变 | 留下半个事实 |

| 重新预览并确认 | 值为 25、修订增加；计算与引用继续走既有影响闸门 | 未刷新、旧值被当作已核对 |
| 选择方案来源后取消 | 无新方案；原输入、运行和正文不变 | 一点“新建”就复制方案 |
| 打开旧报告 | 旧正文与输入面板可打开，任务、候选查询无 500 | ORM 表字段与运行库不一致 |

## 本次发现和修复

1. 项目事实原来有“仅创建 / 创建并录入值”两个按钮，值录入需要第二次提交。现为同一表单、同一服务端事务；原值修改仍走预览票据。
2. 事实列表原来每行重复“编辑 / 证据 / 历史”。现保留直接录入或修改操作，点名称打开详情，再按需查看原文和修订。
3. 报告输入面板原来并列两个新建方案折叠入口和一个仅图标的复制按钮。现只显示“新建”，展开后明确选择输入来源与写作配置。
4. 旧日报告页实际出现 500。只读结构比对发现日常库缺 `report_fact_proposals.proposed_source`、`analysis_candidates.evidence_ids`、`work_tasks.stage`。在备份后补列，并把兼容升级写入 `init_db()`。缺列迁移测试连接并断言 `report_platform_test`。

## 数据保护与恢复

- 升级前备份：`backups/fact-entry-20260927/report_platform.dump` 和 `storage.tar.gz`，均在本机、Git 忽略。`pg_restore -l` 可列出数据库备份，`tar -tzf` 列出 20 个存储条目。本轮没有把备份恢复覆盖日常库。
- 日常库只执行增量 `init_db()`；检查 ORM 模型的表列均已存在。旧候选的新增证据数组默认为空，不补造来源。
- 如需恢复，先停止服务并再备份当前状态，在独立恢复库校验后按 README 的 PostgreSQL 和存储恢复步骤操作。覆盖日常库会丢失备份之后的操作。
